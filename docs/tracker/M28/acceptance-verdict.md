# Verdict · M28 · round 1: BLOCKED

## Blocking findings

- **works, but lies** — A backup that never left the machine is reported exactly like one that reached the object store. Two records identical except for the offsite field - offsite=yes and offsite=no, both with last_success today and outcome ok - produce byte-identical screens: 'Last backup 17 hours ago: the run reported "ok".' cmp on the two captures reports no difference at all. make backup-status is the same. The paragraph underneath then says 'What this does NOT say: whether any of those artifacts is still in the bucket', which for the offsite=no host is worse than silence - nothing was ever sent to any bucket, and the sentence invites the operator to believe something was. This is the out-of-the-box shape: HASHI_BACKUP_ENABLED=0 is the value .env.example ships, and its own comment states the rule being broken - 'a backup that never left the machine is not an offsite backup and must not be reported as one'. The record carries the field and scripts/backup-run.sh due prints offsite=no, so the data exists; both surfaces an operator is pointed at drop it. It goes straight at the milestone's first line, and at the original complaint that started M28 - a backup script that said it was doing something it was not. (/panel/ backup status card, and make backup-status, for any record with offsite=no and a successful run) [screen:04-healthy-success-today-007.png, screen:05-ok-but-never-left-host-008.png, screen:cli-05-offsite-indistinguishable.log]
- **works, but lies** — The panel refuses to assume anything from a damaged record and sends the operator to make backup-status, which then presents the same file as fact and exits 0. With an unparseable record the panel says 'not readable... Nothing has been assumed from it - this screen is not telling you backups are working and not telling you they are failing. Read it on the host with make backup-status.' That command prints 'scheduled: 04:00 Etc/UTC (configured) / last success: never / last attempt: never' and exits 0 - indistinguishable from a genuinely fresh host, with no hint that the file could not be read. The command clearly CAN say so: with the file absent it prints a proper 'No backup has ever been recorded on this host' page and exits 1. Only the damaged case is silent. The same command also does no validation whatsoever: a record with schema 99, or with a 1000-character outcome string containing a script tag, is printed verbatim as fact while the panel correctly calls that same file unreadable. (make backup-status, on a record the panel reports as not readable) [screen:09-unreadable-record-012.png, screen:33-probe-newer-schema-049.png, screen:cli-04-corrupt-record-cli-vs-panel.log]
- **works, but lies** — The panel labels the missed-backup dates 'most recent' and shows the oldest ones. With eight missed days stored ascending - three in August, two on 1-2 September, three on 20-22 September - the panel printed 'Days with no backup at all since this record began: 8 - most recent 2026-08-12, 2026-08-13, 2026-08-14.' Those are the three OLDEST. The three that are actually most recent, the ones from this week, are the ones it dropped. In the state where this matters - a long outage, the exact case the sentence is there to distinguish - it points the operator at six weeks ago instead of at now. Neither surface sorts: make backup-status prints the same list in the same stored order under the same 'most recent:' label, and both simply trust whatever order the writer happened to use. Whichever order that is, one of the two surfaces is mislabelled, and nothing on either enforces the invariant the word depends on. (/panel/ backup status card, missed-days sentence; and the 'days with no backup' line of make backup-status) [screen:07-six-weeks-of-silence-010.png, screen:06-exit3-and-missed-days-009.png]
- **works, but lies** — make backup blames the backup keypair for a failure that has nothing to do with it, and the remedy it prescribes would orphan every existing backup. On this host HASHI_BACKUP_AGE_RECIPIENT is set and non-empty, yet make backup printed a compose error about a different missing variable and then the full 'This dump is encrypted before it is written, so it needs the PUBLIC half of your backup keypair in HASHI_BACKUP_AGE_RECIPIENT... age-keygen -o hashi-backup-identity.txt' page. Supplying the variable it named moved the cause to the next missing one and printed the same keypair advice again - so the guard reports 'your recipient is missing' for any env-interpolation failure. An operator who follows it generates a new keypair and pastes the new public key into .env, after which every artifact already in the bucket is addressed to an identity they have just replaced. The contrast is sharp within the same feature: make restore-from-bucket meets the same class of failure and names the exact keys - 'these keys are missing or empty in .env: HASHI_PRIVATE_HOST HASHI_PRIVATE_PORT HASHI_OPERATOR_USERNAME HASHI_OPERATOR_PASSWORD_HASH' - and points at make hash-password. (make backup, when any variable in the compose env file is missing) [screen:cli-01-backup-status-and-misdiagnosis.log, screen:cli-02-restore-refusal-ladder.log]

## For the owner (not blocking)

- **works, but awkward** — A record dated in the future reads as the reassuring state, and stays there. A record whose last success is 2027-06-01 - eight months ahead - renders as 'Last backup less than an hour ago: the run reported "ok".' A host whose clock jumped forward, took a backup and then had its clock corrected would sit on that sentence indefinitely: the age never grows, so the card can never reach 'failing' or 'nothing has been trying'. make backup-status is better here - it prints the date verbatim, so an operator reading the CLI can see it. The panel, which is the surface built to be read without going to look, is the one that hides it. The rest of this feature is careful about clock and zone skew, which is why this stands out. (/panel/ backup status card, any record whose timestamp is ahead of the host clock) [screen:32-probe-future-timestamp-048.png]
- **works, but awkward** — Exit 3 is reported as a code and never as the different action it is supposed to mean. The design is explicit that 1 and 3 'call for different actions' - 3 means the artifact is on the disk and only the upload failed, and the remedy is make backup-upload FROM=<path>. The panel says 'the run reported "upload-failed", exit 3' and make backup-status says '(upload-failed, exit 3)'. Neither says the artifact is still on the machine, and neither names make backup-upload. The docs themselves say the failing run prints that remedy to cron output, which 'on most hosts is nowhere anybody looks', and that 'the record is the channel that does not depend on mail existing' - so the channel that is meant to be read is the one that drops the remedy. The panel already names the right next command in other states ('make backup-schedule is idempotent'), so the pattern exists. (/panel/ backup status card and make backup-status, on a record whose last failure is exit 3) [screen:06-exit3-and-missed-days-009.png]
- **works, but awkward** — The Settings screen - 'what this control plane is running with, and where each value is changed' - lists no backup setting at all. No HASHI_BACKUP_ENABLED, no endpoint or bucket, no indication whether an age recipient is configured. It does list HASHI_SECRET_KEY as 'configured' and its row even mentions backups ('every backup of them becomes unreadable'), so the pattern for showing a configured-or-not secret is already there. An operator asking 'is uploading even switched on?' has no panel answer anywhere, which is what makes the offsite finding above reachable rather than theoretical. (/panel/settings) [screen:31-settings-backup-rows-047.png, screen:30-settings-046.png]
- **works, but awkward** — make backup-status does not notice the state the panel calls 'nothing has been trying'. With a success 12 days old and nothing failed since, the panel says 'Nothing has been backed up on this host for 12 days, and nothing has failed either - so nothing has been trying' and names make backup-schedule as idempotent. The CLI prints 'last success: 2026-09-11 (ok) / last attempt: 2026-09-11 (ok, exit 0)' and stops, with no remark that the schedule looks uninstalled. An operator on the box over SSH - which is the situation the CLI exists for, and the situation on the day the panel is unreachable - gets no hint. (make backup-status, on a record with an old success and no failure since) [screen:08-nothing-has-been-trying-011.png]
- **works, but awkward** — A word slip in the installed cron entry's own comment: 'The record at .../backups/state is the account that does not depend on mail existing.' It should read 'the channel', as the runbook has it. It is written into the user's crontab, so it outlives the terminal that printed it.
