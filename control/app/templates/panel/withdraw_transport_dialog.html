{# Confirming a withdrawal. UI-PATTERNS §3: a destructive action confirms in a dialog, and the sentence spells out the blast radius rather than asking "are you sure". Here the radius has a half that an operator is very likely to get wrong, and it is the half services/nodes.py insists on: withdrawing changes what the control plane DELIVERS, not what the host is running. A person who already holds a fetched configuration keeps connecting on it until the node is applied without them — so "withdrawn" read as "stopped" is the opposite of what happened, and this is the last moment to say so. The other half is what this action is NOT. Taking a protocol out of the fleet's offer and taking a person's access away are two different operations with two different blast radii; revocation destroys that person's material everywhere, and it is on the Users screen. Naming it here is what keeps an operator from reaching for this one. THE HALF THAT TURNED OUT TO BE FALSE — M18's acceptance. "until the node is applied without them" is a promise about an apply that, on the node's LAST enabled row, never comes: rendering nothing is refused (apply.NOTHING_LEFT_TO_APPLY), so the operator who withdraws to cut somebody off, presses apply and reads "nothing on the node was changed" has every reason to believe access is gone. It is not. The second arm below says so before the press, in the same place the plain one does, and it names the only way out the product has along with what that costs. It says WHATEVER THIS NODE IS ALREADY SERVING rather than "it keeps serving this transport", which is the same fact on an applied node and not a claim at all on one nothing was ever pushed to. The row's own standing sentence and the toast still make the stronger claim; that is the same defect one surface over and is recorded rather than widened here. AND IT IS NOT SAID AT ALL ON A NODE NOTHING HAS EVER REACHED — M18's acceptance, round 2, which read that sentence unchanged on a node whose address does not resolve while the apply refusal one press away opened "No transport on this node has ever been applied". ``never_applied_here`` is the column that refusal reads, so the two agree by construction, and the arm it selects claims only what the ROWS can support: that nothing this panel holds has ever been pushed. Not that the host is serving nobody — a removed row takes its stamp away with it, and what is on the host is not visible from here. No key material is named and none could be: this dialog's whole context is one OfferRow, which carries a name, a standing, a flag and an id. #}
