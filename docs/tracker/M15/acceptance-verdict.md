## Could not check

THE STAND CANNOT SHOW THIS: (1) That the two amneziawg instances actually bind different UDP ports and both come up. Nothing here was ever applied to a host - db:SELECT applied_at, applied_digest FROM node_transports returned null for every row for the whole run, because no node has an SSH key and there is no second machine. On two real hosts a person would have to run `ss -lunp | grep 5182` on the entry after applying it and see two awg interfaces listening, one on 51820 and one on 51821, and `wg show` (amneziawg-tools) listing both with distinct keys. (2) That the hop carries traffic and that the friend-facing kernel-tunnel refusal is the right call rather than an over-strict rule. On the entry and the leaf a person would have to bring a friend's AmneziaWG config up, then `curl -s ifconfig.me` from the friend's device and see the LEAF's public address, not the entry's - and, for the refused shape, confirm the entry's address appears instead, which is the silent failure the refusal exists to prevent. (3) That removing a transport actually frees the port ON THE HOST. I proved it frees the row, the port and the config name in the control plane, and the panel says plainly 'The node is still configured to serve it: apply it to stop that' - but whether the apply after a removal really tears the interface down on the box is a field observation: `ss -lunp` on the entry before and after, plus `ls /etc/amnezia*` or the node stack's config directory showing the file gone. (4) That the 'cannot render' node keeps serving its last successful apply. Mine had never been applied at all, so I saw the state left alone but not the 'serving a configuration you did not choose' half of it.
