## Could not check

Six things. (1) The bare host was bare but not virgin: it was a fresh clone with its own .env, its own volumes and no crontab entry, on the same machine as the stand's Docker engine - I had no second machine. (2) `make restore-from-bucket` refused on its first run because this host runs ufw with LOGLEVEL=low, and the refusal was correct and clearly worded ('sudo ufw logging off ... a second run is safe'); I am not permitted to change a firewall's logging, so I ran the rest of the walk with ufw off PATH, which the bootstrap reports as 'no ufw on this host, so nothing here switches connection logging on' - i.e. I measured the shape of a host that has no ufw, not one whose logging was turned off. On a stock Ubuntu box this guard means the headline command is one command plus one sudo line the command itself prints. (3) The object store was a minimal S3-protocol server I wrote for the walk, because no registry image was reachable; it proves the protocol path, the object names, the ETag check and that the host only ever PUTs, and it proves nothing about real bucket versioning, object lock or a lifecycle rule - whether the write-only credential is genuinely write-only is enforced at the provider and is a documented decision I could not exercise. (4) 'Apply the existing node' after the restore could not complete: the panel refused with 'this node has no SSH key on its record, so no connection was attempted and nothing on the node was changed', which is correct - there is no leaf host on this stand and I never gave the node a key - so the restore is proven down to the panel and the subscription, not down to a node actually reconfiguring itself. (5) /sub on the restored host could not be reached from outside it: Caddy asks a public CA for a certificate for a name that does not resolve, exactly as the runbook says it will, so I verified the subscription from inside the compose network instead - where it returned the byte-identical body for the same token. (6) The unattended daily run was proven by installing the real cron entry and running the tick the way cron runs it, not by waiting out a real 04:00. And nothing on this stand says anything about whether a tunnel survives a Russian mobile whitelist shutdown; that is a field observation and this walk does not cover it.
