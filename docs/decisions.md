# hashi — decision journal

<!--
WHAT: One line per decision that the NEXT run has to know about. Read first,
      appended to last, by every persona this project consults.
WHY:  a persona has no memory between runs. Without this, every question starts
      from zero and the owner repeats context they gave an hour ago. The
      short-term half of memory (the last N exchanges) lives in the Warden's
      state volume and is deliberately forgettable; THIS half is durable — it
      survives rebuilds, quota resets and container wipes, and the owner can
      read and correct it.
HOW:  append at the bottom. Never rewrite a line: a decision that was reversed
      gets a NEW line saying so, because "we changed our mind in March" is
      itself the thing a later run needs to know.

**The test for whether a line belongs here:** *if the next run does not know
this, will it decide wrongly?* If no, it is not a decision — it is progress, and
progress belongs in the task's own files.

Good: "chose Postgres over SQLite — the fleet writes concurrently and SQLite
locks." Bad: "implemented the login screen."

| 2026-08-09 | An entry→leaf hop is two ordinary `node_transports` rows marked with a `purpose` and pointing at each other, not a table of its own; and which of a transport's values are SYMMETRIC is declared by the transport (`KeySpec.shared_between_peers`). | Reusing the row shape gave the hop key minting, encryption at rest, rotation, apply and drift detection for free, with no `if this is a relay` in any of them — the cost is one filter on the subscription query, which is where the danger is anyway. The declaration exists because `control` mints each end separately: two independently minted pre-shared keys produce two VALID config files and a handshake that never completes, and the only way to know which value is symmetric without recognising it by name is to be told. |
| 2026-08-09 | The e2e stack gets a second `--env-file` (`deploy/e2e.env`, committed and fake) rather than depending on the owner's real `.env` being complete. | The owner's `.env` had no operator credentials, so `make e2e-up` failed at compose interpolation and the acceptance suite had never once run — several scenarios in it were wrong in ways only a real boot could show (a scenario comparing transport DIRECTORY names against DECLARED names could never have passed). A suite whose stack cannot start is not a suite. |
| 2026-08-09 | Upstream data-plane image pins moved from `control/app/services/apply.py` to `edge/bootstrap/node_stack.py`, keyed by `ConfigFormat`. | A wg-quick transport needs a different daemon, different capabilities and a different file extension than an Xray one. | 2026-08-08 | The control image now runs the INSTALLED distribution, not a copied source tree (`WORKDIR /src` → install → `rm -rf /src` → `WORKDIR /app`), and `pyproject.toml` finds packages (`[tool.setuptools.packages.find] include = ["control*", "edge*"]`) instead of listing them. | The image installed the package and then imported it from the copied tree, because cwd wins on `sys.path` — so packaging was never exercised. Proved: with the old explicit list, a new `edge/transports/` package was absent from the installed distribution (`discover()` → `[]`) and shipped only by accident. The charter's fourth criterion needs packaging to follow the directory. |
| 2026-08-08 | Caddy is BUILT from `deploy/docker/caddy.Dockerfile` (upstream tag still pinned) instead of pulled with the Caddyfile bind-mounted. | A bind mount is resolved by the docker DAEMON. Against any engine that does not hold this checkout — the fleet's dind, a remote host — the path is missing, Docker creates a directory there, and the stack fails to boot. Config must travel with the image. |
| 2026-08-08 | The dev overlay's publish address is `${DEV_BIND_ADDR:-127.0.0.1}`, and the e2e stack has `E2E_BIND_ADDR` (default `127.0.0.1`). | Loopback-only is right for a laptop and impossible for an isolated dind engine, where `127.0.0.1` is dind's own loopback and no runner can reach the stack. The default is unchanged; an engine that is not your machine is an explicit per-run opt-in. |
| 2026-08-08 | The e2e stack pins `HASHI_PUBLIC_HOST=localhost` via `deploy/docker-compose.e2e.yml` rather than inheriting the owner's real one from `.env`. | Caddy cannot obtain a certificate for a name that does not point at the test machine, so it retried ACME forever and never served a request — every proxy-path scenario was silently testing nothing. Against a name that IS real, each test run would ask a public CA for the production certificate and burn its rate limit. `localhost` is served by Caddy's internal CA, with no CA on the internet involved. |
| 2026-08-08 | `/openapi.json` is now off (`openapi_url=None`), not just `/docs` and `/redoc`. | Turning off the two HTML viewers left the machine-readable schema — every route, parameter and model — served to anyone. Found by the first e2e run against a real socket; the unit test had only ever asked for `/docs` and `/redoc`. |
| 2026-09-08 | **Decision 5 — `ufw` logging is off and the existing `/var/log/ufw.log` is deleted**, on both field hosts, before any traffic test in this run. | The charter forbids the record *at any level*, and `ufw enable` — the runbook's own line — turns logging on by default and starts writing source addresses. 5840 bytes of it existed on the leaf. Deleting rather than rotating is safe here because both hosts are test hardware whose data is expendable, and keeping it would mean the fleet's own verification created the one record the project exists to not hold. The lasting half of this is not the deletion: it is `ufw logging off` becoming a line in `scripts/node-bootstrap.sh` (M11) and in the runbook (M6.2), so the next host never collects it in the first place. |
| 2026-09-09 | **The plain-WireGuard image pin stays as it is**, with its limitation recorded rather than fixed: `masipcat/wireguard-go:0.0.20230223` ships `iptables` on the **legacy** backend while `amneziavpn/amneziawg-go:3.0.3` ships the **nft** one. On a `ufw` host — which every node this project bootstraps is — the two backends are independently traversed hooks, so the legacy `-I FORWARD 1 … ACCEPT` M14 renders cannot front-run ufw's nft `DROP`. `amneziawg` is proven end to end on real hardware; a friend-facing `wireguard` row is **not proven and is likely to fail silently** in exactly M14's shape: handshake completes, nothing moves, nothing logged. | Owner's call, taken 2026-09-09 during the field run, because changing an image pin is an architect decision under `CLAUDE.md` and not one an overnight run may take for itself. Recording beats fixing here for three reasons: `amneziawg` is the transport the runbook already **mandates** for the entry→leaf hop and recommends for Shape A, so the proven member is the one the fleet actually depends on; the plain-WireGuard transport is `hop_capable=False`, so the exposure is narrow — a friend-facing `wireguard` row specifically; and the rendered config is **correct**, so this is one packaging fact about one pinned image rather than a defect in the code. The detail and the evidence are in `docs/tracker/M14/carry-over.md`. Revisit by finding a plain-WireGuard image on the nft backend, or by rendering backend-aware rules — both are new work, not a tweak. |
| 2026-09-09 | **Decision 3 — when the hop is down, an entry node fails CLOSED.** A friend connected to an entry node whose hop to its leaf is unavailable gets **no exit at all**, never a local one. | The owner's answer of 2026-09-08, implemented in M3. The alternative — falling back to the entry's own `freedom` outbound — is the single worst failure this product can have: the friend's traffic exits **in Russia**, from the address the panel is happy to call healthy, and nobody is told. Every visible signal stays green while the exact protection the two-node topology exists to provide is gone. A friend who cannot connect asks why; a friend silently exiting in Russia does not know to ask. Note this is also why M3's acceptance cannot be discharged by reading a rendered config: the failure mode and the success mode differ only in where packets emerge, so nothing short of observing the exit address settles it. |
| 2026-09-09 | **The entry node's hop-peer `AllowedIPs` is `0.0.0.0/0`, deliberately.** The control plane's own SSH is protected by a *different* mechanism: `Table = off` on the entry's hop config, plus a source-based `ip rule` for the tunnel's own address into a dedicated table. **Do not re-narrow it** — `docs/PLAN.md`'s M3 prose still describes the old narrow value and now carries a correction beside it. | Discovered implementing M3. `AllowedIPs` is not a firewall list, it is WireGuard's crypto-routing table: a packet is only encrypted to a peer whose `AllowedIPs` covers its **destination**, and a reply is only accepted if its **source** is covered. Return traffic from a relay arrives sourced from the *internet host the friend asked for*, not from the leaf — so a `/32` entry can send nothing but pings to its own peer, and the relay cannot work at all. What made a wide list frightening was the route `wg-quick` derives from it, and that is a separate switch. Verified on the live fleet: with `Table = off` the main routing table still reads `default via <gateway> dev eth0`, only source-routed traffic from the tunnel address enters the hop, and the SSH session the control plane manages the node over survived the apply. |
| 2026-09-09 | **A leaf's in-tunnel address is a route, not a destination** — `exit_address(leaf)` was replaced by `exit_via(entry)`, and the entry reaches the internet with `sendThrough` bound to its own end of the tunnel rather than by dialling the far end. | The plan told M3 to target the leaf's in-tunnel address as an outbound destination. Nothing listens there: a leaf runs one hop end and no proxy, so there is no service to connect to. Had it been built as written it would have produced a rendered config that looked correct and connected to nothing — which is the exact failure this milestone exists to fix, reproduced one level up. Kept as a decision because the plan's original wording is still in the file, now with a correction beside it. |
| 2026-09-09 | **Decision 2 reaffirmed after contrary evidence: Tailscale stays.** Re-put to the owner during the field run once measurement showed `tailscale.com` is filtered from the Russian entry host, with three alternatives offered — a WireGuard management tunnel using the project's own machinery, Headscale, or dropping M7 to the SSH tunnel that already works. The owner chose to keep Tailscale. | The original decision of 2026-09-08 was taken on reasoning; this one is taken on measurement, which is stronger. What the measurement actually shows is narrower than the fear: `controlplane.tailscale.com` and `login.tailscale.com` answer in ~150 ms from that host and the **coordination plane works** — only the marketing site fails its TLS handshake. So the lock-out scenario decision 2 accepted has not materialised; what has been demonstrated is that per-hostname filtering of that company is real, present and selective, which is a reason to keep the SSH fallback of M7.3 genuinely working rather than a reason to change course. The rejected alternative worth remembering is the WireGuard management tunnel: it would have removed the third party entirely and reused machinery this run proved on hardware, at the cost of a bootstrap step that must print the owner's config once, since the panel cannot hand you the config you need to reach the panel. Recorded because a later run may face this question again with the coordination plane blocked, and should know the option existed and why it was not taken. |
