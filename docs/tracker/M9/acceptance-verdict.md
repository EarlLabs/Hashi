## For the owner (not blocking)

- **works, but awkward** — Replace params on one end of a hop silently desynchronises the two ends, and nothing anywhere says so. With the entry-alpha -> leaf-beta amneziawg hop in place I opened Keys & configs -> replace params on the entry end and changed two values: mtu 1420 -> 1400, then init_packet_magic_header 1111111111 -> 1999999999. Both were accepted. The leaf end kept mtu 1420 and init_packet_magic_header 1111111111. The hop row still reads 'pending' with no warning, the Keys & configs rows look normal, and the banner said 'both are still running what they had and the tunnel is unaffected' - true only because neither node had ever been applied. AmneziaWG's magic headers are a wire-format agreement between the two peers; if they differ the handshake is not recognised and the tunnel never completes. The panel knows this hazard by name elsewhere: the same node's transports dialog refuses to withdraw the hop end with 'switching one end off would leave a tunnel that no longer completes while both ends still look configured'. The same sentence applies here and is not said. The establish dialog invites the same mistake at birth by asking for all 11 parameters twice, once per end, with no cross-check and no hint that any of them must match - unlike peer_tunnel_address, which at least carries the hint 'the far end's tunnel address'. Rotation was taught to write both ends together; replace params was not. (Keys & configs -> replace params, on either end of an established hop. Also Hops -> establish hop -> advanced tuning, which collects the same parameters twice with no cross-check.)
