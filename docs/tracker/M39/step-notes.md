Conventions established here. They bind later steps, and later milestones, until
something supersedes them. Everything in docs/tracker/M37 and M38 step-notes binds

## From M39.1 (bot runs as its own container) — commits 4cbd364 + 99f4ca3, review clean in round 2 (round 1 clean; 2 Mediums + 1 Low fixed)

- **Entrypoint** `control/app/botmain.py`, run as `python -m control.app.botmain`, dispatched by `deploy/docker/entrypoint.sh` on `command: ["bot"]` (before the migration step — only `control` migrates). It builds `Settings()`, binds the `SecretBox` (from the secret key) and `apply.bind_settings`, builds `Database(settings.database_url)`, and runs ONLY `telegram_poller.start_poller`/`poll_forever` — no uvicorn, no other lifespan task. Blank token → loud `SystemExit` before any binding. SIGTERM/SIGINT cancel the poller then dispose the pool (graceful `docker stop`). Reuses `main.configure_logging` (the httpx/httpcore token-safety pin is identical). A crashed poll loop re-raises on shutdown (non-zero exit + traceback); `restart: unless-stopped` covers it; the pool is disposed either way. Heartbeat file `HEARTBEAT_PATH` (a string literal in botmain.py), rewritten every 15s; a pin test (`tests/infra/test_the_stand_has_a_fake_telegram.py`, ast-parsed, no runtime import) ties that literal to the compose healthcheck so the two can't drift.
- **The poller left the web app's lifespan.** `control/app/main.py` no longer imports or starts `telegram_poller`; nothing holds `app.state.telegram_poller`. The `telegram_poller` module and its direct unit tests stay. So the control web process NEVER polls — only the bot container does (no double-poll / 409).
- **Compose** `deploy/docker-compose.yml`: service `telegram-bot`, same build/context as `control`, `command: ["bot"]`, **off by default behind the `telegram-bot` compose profile**, outbound-only (no ports), non-root, `restart: unless-stopped`, heartbeat healthcheck, `depends_on: control service_healthy`. Its env is the full control `Settings` block via the `&control-environment` YAML anchor PLUS `HASHI_TELEGRAM_BOT_TOKEN/OWNER_ID/API_URL`; **those three were removed from the `control` service**. A read-only delivery-cert mount for apply parity. The bot needs the full Settings (not just DB_URL+SECRET_KEY) because `Settings()` won't boot without `operator_password_hash` and links need `public_host`/`public_https`.
- **Enable it:** `make up PROFILES=telegram-bot` (new `PROFILES ?=` var threaded through `COMPOSE`; plain `make up` unchanged). `.env.example` bot section says so.
- **Known-deferred to the next step (the stand e2e re-point):** `make e2e-verify` is RED until it — the stand's `control` (`docker-compose.e2e.yml`) still carries the Telegram env but no longer polls, and the bot profile isn't enabled on the stand. GOTCHA for the re-point: the `telegram-bot` profile is in the BASE compose, so it is NOT in `E2E_ALL_PROFILES`; enabling the bot on the stand without moving the profile into the overlay (and widening `E2E_ALL_PROFILES`, which `test_down_takes_away_every_profile_up_can_start` ties to the overlay's profiles) would let `make e2e-down` leave a bot container behind. The stand bot also needs `HASHI_PUBLIC_HTTPS=false` (the e2e overlay sets it only on `control`, so the bot would otherwise render `https://localhost/sub/...` and break link-equality).
- **Ready line to assert, now from the bot container's log:** `INFO control.app.services.telegram_poller: telegram: polling as @hashi_e2e_bot`.
- **For M40 (leaf egress):** the bot is a normal container on the compose default network; its two outbound flows are the Telegram Bot API (`HASHI_TELEGRAM_API_URL`) and SSH to nodes on apply — a leaf egress must carry both (or at least the Telegram one).

## From the stand re-point + docs step — commit 94ded0b, review clean in round 1

- **The stand runs the bot as its container.** `deploy/docker-compose.e2e.yml` has the `telegram-bot` service switched on, pointed at the fake Telegram (`HASHI_TELEGRAM_API_URL=http://telegram:8081`, fixture token, owner `424242`), with `HASHI_PUBLIC_HTTPS=false` so its `/sub/` links match the plain-HTTP stand. The three `HASHI_TELEGRAM_*` vars and `depends_on: telegram` were removed from the stand's `control`; the bot depends on both `telegram` and `control` healthy.
- **Teardown:** `make e2e-up` forces the profile on (`override E2E_PROFILES += telegram-bot`), and `E2E_ALL_PROFILES := browser telegram-bot`, so `make e2e-down` removes the bot too (nothing left behind). The e2e conftest adds `--profile telegram-bot` so `ps`/`logs` see the bot.
- **Bot container on the stand:** `hashi-e2e-telegram-bot-1` (service `telegram-bot`, project `hashi-e2e`). Ready line in ITS log: `INFO control.app.services.telegram_poller: telegram: polling as @hashi_e2e_bot`. The scenario reads `logs_of("telegram-bot")` for the ready line and the stranger-never-named check.
- **The acceptance stand gets the bot for free:** `scripts/acceptance/stand.sh up` runs `make e2e-up E2E_PROFILES=browser`, and `e2e-up`'s `override +=` appends `telegram-bot`, so the acceptance (and security) stand come up with the bot running. Unchanged `stand.sh`.
- **Runbook** "Switching it on" now describes the container: `make up-panel PROFILES=telegram-bot`, ready line in the bot container's log, and a plain note that on a Russian host the bot sits in "polling is failing" until M40's leaf egress.
- **For M40 (leaf egress):** the bot is a normal container on the compose default network, outbound-only; its two outbound flows are the Telegram Bot API (`HASHI_TELEGRAM_API_URL`) and SSH to nodes on apply. On the real Russian host neither the bot nor control can reach `api.telegram.org`; M40 must carry the bot's outbound (at least the Telegram flow). The bot renders links from the shared `&control-environment` anchor + overlay, so keep that parity when adding egress.
