WHY IT EXISTS: the add-node dialog calls this key optional — *"without it the node can be registered but its configuration cannot be applied"* — and until this dialog there was nothing that could supply one afterwards. The real-host walk found every candidate route 404ing, which made a node registered on that invitation permanently unappliable, permanently unreachable by a revocation, and only ever retirable. Everything else on a node record still stays fixed; a new host is still a new node. THE BOX IS WRITE-ONLY, and it is the same exception the add-node dialog's key box is: UI-PATTERNS §9 and CLAUDE.md say the panel states the rule where key material could appear, and this is how the control plane is given the credential for reaching a host. It is stored encrypted and never rendered anywhere again — which is why this template is handed `has_key`, a boolean, and never the value behind it. It is NEVER refilled on a refusal, unlike every other form in this console: putting a submitted private key back into the markup would make the panel a place key material appears. The refusal under it quotes no part of what was pasted either — it is a sentence about the shape of a key (services/nodes.py, SSH_KEY_UNUSABLE). #}
