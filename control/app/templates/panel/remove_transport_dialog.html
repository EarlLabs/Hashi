{# Confirming a removal — M15.2. UI-PATTERNS §3: a destructive action confirms in a dialog, and the sentence spells out the blast radius rather than asking "are you sure". This is the most destructive thing the Nodes screen can do to a row, and it is one dialog away from an action that sounds like it and is not — so the two halves an operator can get wrong are both stated: * what removing takes that withdrawing does not — the row itself and every user's material on it, minted again from scratch if the transport is ever enabled here again. Withdrawing keeps both and puts the protocol back with nobody re-importing anything; that is the door out of this dialog, and it is named. * what removing DOES NOT take — the daemon on the host. The row leaves this panel immediately and the node keeps serving what it was last given until it is applied, which is the same thing services/nodes.py insists on for withdrawing and is sharper here, because the operator has just watched the row disappear. The other half of why this exists is the one nothing else in the panel says: the listening port and the config name are held by the row, switched off or not, so this is the only action that gives them back to the node. An operator who followed the runbook into a collision is reading this dialog to get out of it. AND ON THE NODE'S LAST ENABLED ROW THE SECOND OF THOSE WAS FALSE — M18's acceptance. "until it is applied" is a promise about an apply that never comes: a node rendering nothing is refused (apply.NOTHING_TO_APPLY_YET), so the operator who removes the last transport to cut everybody off, presses apply and reads "nothing on the node was changed" concludes access is gone while the container is still up and still authorising everyone who held a credential on it. Measured on a real applied host. The second arm below says so before the press, and its way out is NOT the withdrawal dialog's: a removed row cannot be offered back, so what is owed here is enabling a transport on this node and applying that — which is what takes the removed one's service away with it, since the apply brings the node's compose file down to what is enabled now. It says WHATEVER THIS NODE IS ALREADY SERVING rather than "it keeps serving this transport": the same fact on an applied node, and not a claim at all on one nothing was ever pushed to. The row's own standing sentence and the toast still make the stronger claim; that is the same defect one surface over and is recorded rather than widened. The title is offer.transport, which is services/console.py's placed_as: on a node running two instances of one protocol it reads `amneziawg (amneziawg-2)`, so the confirmation cannot name the wrong one of two. No key material is named and none could be — the whole context is one OfferRow, which carries a name, a standing, a flag and an id. #}
